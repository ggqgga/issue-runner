# 실전 가동 케이스 스터디 — 첫 무인 배치 기록

> 2026-06-12, 비공개 Rails 프로젝트(이하 "프로젝트 A")에서 issue-runner를 처음 실전
> 가동한 기록이다. 프로젝트 식별 정보는 익명화했고, 수치·타임라인은 실측 그대로다.

## 설정

- 루프: 별도 터미널에서 `/loop 15m /issue-runner`, `MAX_AGENTS = 2`
- 대상: 프로젝트 A의 실이슈 3건(P1 버그 1 + 기능 2) + issue-runner 자체 이슈 1건
- 이슈는 기획 세션에서 loop-issues 트리아지로 마감 — 하드웨어가 필요한 이슈들은
  agent-ready 없이 남겼다(무인 워커가 못 하는 일은 큐에 넣지 않는다)
- CI: GitHub Actions 없이 local-ci (`bin/ci` = rails test + rubocop 체인)
- 사람의 역할: **이슈 작성과 PR 리뷰·머지, 둘뿐** (구현·테스트·CI·정리에는 무개입)

## 결과 요약

| 항목 | 값 |
|---|---|
| 처리 이슈 | 4건 (P1 버그 1 포함) |
| PR | 4건, 전부 사람 리뷰 후 머지 |
| 변경 규모 | 합계 약 +485 / −54 |
| local-ci 첫 시도 통과 | 4 / 4 |
| needs-human 승격 · warn · 타임박스/서킷브레이커 발동 | 0 · 0 · 0 |
| 디스패처 수동 개입 | 0회 |

## 타임라인 (UTC)

```
D0 19:05  첫 틱 — 이슈 2건 claim, 두 워커가 동시에 PR 오픈 (둘 다 첫 시도 CI green)
          이때 세 번째 이슈는 본문의 "Blocked by #<버그이슈>" 라인 때문에 자격 미달
   ~6h    사람 부재 — 시스템 전체가 머지 대기로 조용히 정지 (재시도·폭주·토큰 낭비 없음)
D1 01:16  사람이 PR 2건 머지
D1 01:18  다음 틱 — 머지 정리 + 블로커가 닫힌 세 번째 이슈가 자동 해금되어 claim
D1 01:21  네 번째 이슈의 PR 오픈 (claim → PR 약 3분)
D1 01:29  세 번째 이슈의 PR 오픈 (claim → PR 약 11분, 커밋 3개 — 검증자 지적 반영 포함)
D1 02:22  사람이 머지 — 배치 종료
```

## 검증된 메커니즘

1. **DAG 스케줄링** — `Blocked by #N` 전용 라인이 차단 → 블로커 머지 → 자동 해금 →
   디스패치로 정확히 동작했다. 처음에 이슈가 안 집힌 이유가 슬롯 부족이 아니라
   의존성이었음이 사후에 확인됐다.
2. **사람 머지 게이트의 고장 모드** — 사람이 6시간 자리를 비우자 시스템은 폭주하는 대신
   멈췄다. "막히면 멈춘다"가 실측으로 확인된 첫 사례.
3. **local-ci 파이프라인** — Rails 테스트 체인을 무인 워커가 4번 모두 첫 게시에 통과.
   결과는 commit status로 PR에 표시되어 웹 머지 화면에서 확인 가능했다.
4. **검증자(codex) 게이트** — 4건 중 3건에서 작동: 그중 한 PR은 커밋 3개로 끝났다
   (검증자 지적 → 해결 커밋 → 재검증 후 종료). 검증자가 완료된 PR 기준 BLOCKER 미해결
   종료 0건. 나머지 1건은 워커가 검증자 단계에 도달하지 못했다 — 아래 개선 후보 1 참조.
5. **claim/슬롯 규율** — MAX_AGENTS=2 정확히 준수. 경합·중복 claim 0건.

## 발견된 개선 후보

1. **워커의 검증자 단계 증발 미감지** — 한 PR은 끝까지 `## 검증자 리뷰` 섹션이 달리지
   않았다(워커가 codex 리뷰 단계에서 사망 추정). CI green이라 머지에는 지장이 없었지만,
   시스템이 이 상태를 감지·복구하지 않는다. Maintain에 "pr_open + 검증자 섹션 부재 +
   워커 사망 → 검증자만 스폰"하는 경량 보수 경로가 후보.
2. **시스템 레포 PR의 가시성** — 대상 프로젝트 PR은 바로 머지됐지만 issue-runner 자체
   레포의 PR은 사람 시야에서 빠져 한참 대기했다. 틱 Report에 머지 대기 목록을 레포별로
   명시하는 것이 후보.

## 운영 메모

- 사람 머지 속도가 곧 처리량이다 — 슬롯이 머지 대기에 묶이는 것은 의도된 설계.
- PR은 워커의 종료 보고(= `## 검증자 리뷰` 섹션이 달린 뒤)를 확인하고 머지하는 것이
  깔끔하다. 그 전에 머지하면 검증자 후속분이 별도 PR로 쪼개진다.
