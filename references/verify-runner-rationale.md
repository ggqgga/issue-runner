# verify-runner 설계 근거 — 사고 이력과 버린 대안

`skills/verify-runner/SKILL.md` 는 **틱 골격**이다 — 무엇을 어떤 순서로 하라는 지시만
담는다. 그 지시가 **왜 그 모양인지**(어떤 사고가 있었고, 어떤 대안을 왜 버렸고, 어느
이슈 번호가 근거인지)는 여기 있다. SKILL 의 문단 끝 `(근거: verify-runner-rationale §N)`
가 이 문서의 절을 가리킨다.

**이 문서는 규범이 아니다.** 틱 수행 중에는 읽을 필요가 없고, 여기 적힌 문장이 SKILL 의
지시와 어긋나 보이면 SKILL 이 이긴다. 규범 SSOT 는 `references/state-machine.md`(소유권·
정지·전이 실패)와 `references/loop-conventions.md`(세 루프 공용 규약 §1~§10)다.

## §1 왜 검증이 전용 루프인가 — 3루프 분리

예전에는 이 검증을 issue-runner 가 디스패치한 **타임박스된 일회성 워커** 안에서
인라인으로 시켰다. E2E 는 헤드리스 크롬 10개를 띄우고 codex 는 외부 CLI 라 느린데,
워커가 그 느린 일을 끝내기 전 죽거나 시간초과되면 PR 이 드롭됐다(동시 5워커면 5배로
샜다). 검증을 **버리지 않고 매 틱 재집는 전용 루프**가 소유하면 드롭이 원천 불가하고,
직렬(MAX_VERIFY=1)이라 크롬 부하 피크가 한 세트로 고정돼 박스가 안 터진다. 이것이
issue-runner(생산)→verify-runner(검증)→closeout(마감) 3루프 분리다.

## §2 codex 는 왜 PR 당 2회인가 (#375)

리뷰어(codex)는 같은 diff 에 회차마다 다른 답을 낸다 — 같은 head 를 세 번 물었더니
P1 → P2 → CLEAN 이 나온 실측이 있다. 세 번째부터는 게이트가 아니라 발산이다. 그래서
상한을 2 로 두고 3회차는 자체 리뷰로 완료한다(사용자 결정 2026-09-13, #375 ·
Plans/review-round-cap-and-gate-signals.md).

3회차가 codex 없이도 서는 이유: codex 는 이 PR 에 이미 두 번 답했고 워커가 두 번 고쳤다.
남은 판정은 "직전 지적이 해소됐는가" 이고 그건 diff 대조로 선다.

E2E·결정적 CI 실패에 회차 카운터를 같이 올리면 안 되는 이유: 카운터를 같이 올리면 E2E 실패
두 번에 codex 를 한 번도 못 받고 3′ 로 간다.

옛 상한(3회 초과 → `hold:policy`)은 폐기했다 — **리뷰 반송은 사람 결정 사유가 아니다.**
사람 호출(`needs-human`)은 재심이 "사람 몫 유지" 로 끝났을 때만 붙는다(#244).

## §3 VERIFIER 계약과 타임아웃 값의 단일화 (#427)

`VERIFIER` 출력 계약을 issue-runner `SKILL.md` 한 곳으로 모은 이유: 세 SKILL 이 각자
자기가 SSOT 라고 자칭하고 있었다.

`VERIFIER_TIMEOUT_MIN` 을 `scripts/lib/constants.sh` 의 `CODEX_GATE_TIMEOUT` 환산으로
못박은 이유: 종전 산문은 "900s = 10분" 이라 두 값이 어긋나 있었다. 게이트가 기다리는
시간보다 스폰 데드라인이 짧으면 정상 리뷰를 끊어 놓고 "미산출" 로 적게 된다.

## §4 보조 리뷰어가 비게이트인 이유

`AUX_REVIEWERS` 는 Codex 와 겹치는지 대조 기록을 쌓는 단계다. 판정에 넣을지(게이트
승격)는 그 기록이 쌓인 뒤 사람이 정한다(사용자 결정 2026-09-05).

## §5 `verifying` 은 경합 방지가 아니다 (#275 · #276)

이 루프는 단일·직렬(MAX_VERIFY=1)이라 레이스가 없다. 점유 라벨 `verifying` 은
**가시성과 사망 증거** 용이다 — 루프 현황(`loop-status.sh`)에서 `검증대기`(`flow:verify`)
줄과 `verify-runner`(`verifying` — 지금 들고 있음, 수십 분) 줄을 가르는 근거이고(#276),
① 이 "이전 틱이 죽었다" 를 판정하는 유일한 흔적이다.

모든 종료 상태가 이 라벨을 떼기 때문에 "`verifying` = 지금 이 순간 검증이 돌고 있다" 가
항상 참이고, 재시도 대기는 검증대기(`flow:verify`)다.

## §6 표면 교정을 반송하지 않는 이유

반송 한 바퀴(이슈→디스패치→구현→검증→마감)를 한 줄 고치자고 돌리는 게 낭비이고, 이
레포에선 틀린 주석이 실제 결함의 진원이기 때문이다(오서술 하나 고치려고 PR 하나가 따로
돈 전례가 있다).

판정 기준을 closeout 3단계 "표면 교정 흡수" 와 **같은 한 줄**(`loop-conventions.md` §10)로
묶은 이유: 두 루프가 다른 경계를 쓰면 같은 발견이 어느 루프에 걸리느냐로 처분이 갈린다.

절차의 각 단계가 왜 있는지:
- **재게이트** — 커밋을 얹으면 로컬 CI 캐시가 SHA 기준이라 `ci=revalidate` 가 되고, 안
  채우면 closeout 이 막힌다.
- **공개** — 자기가 고친 것을 자기가 그린라이트하는 구조라, 그 사실이 closeout·사람에게
  보여야 한다.
- **E2E 미재실행** — 주석은 실행되지 않는다. 결정적 CI 재통과로 충분하다.

## §7 드롭 회수에 별도 스윕이 필요 없는 이유

`flow:verify` 는 다음 틱 FIFO 로, `verifying` 은 고아 우선으로 재집힌다 — 구조가 곧
회수다. 그래서 closeout ①-b 가 하던 완결 유실 회수 중 **검증 단계** 몫을 이 재집이
흡수했고, verify-runner 는 스윕 절을 갖지 않는다.

`고아 재집` 한 줄을 ④ Report 에 남기는 것은 사망 증거다 — 다음 사람이 왜 두 번 돌았는지
안다.

## §8 인프라 자가체크를 반송하면 안 되는 이유 — brakeman 전례 (#2768)

PR diff 와 인과로 닿지 않는 실패는 반송해도 워커가 고칠 수 없어 반송 자체가 낭비다
(무한 반송 → 이슈만 오염).

전례: brakeman `--ensure-latest` 는 상류가 패치 릴리스를 내는 순간 **스캔을 시작도 안
하고** exit 5 로 죽어(출력이 버전 한 줄뿐, 경고 리포트 없음) 코드와 무관하게 전 브랜치를
동시에 빨갛게 만들었다. PR 7건이 12틱 묶였고 재실행은 영원히 무의미했다(`bin/brakeman`
에서 그 플래그를 제거해 해소 — #2768).

"전 브랜치 동시 빨강" 이 지문인 근거: 그 PR 들이 서로 다른 파일을 건드리는데 같은
지점에서 죽을 확률은 없다.

## §9 E2E 자기포화 플레이크 (#981)

`test:system` 스위트는 10코어에 크롬 10개 병렬이라 한적한 박스에서도 스위트 자기포화로
저장-계열 어서션이 런당 ~1개 깜빡인다(단독 실행은 통과). 그래서 스위트 실패를 곧바로
진짜 실패로 읽지 않고 파일-단독 재실행으로 가른다.

직렬 레인이라 이 느린 재확인을 감당한다 — 예전 per-test 재시도 하네스가 게이트에서 하던
일을 여기서 루프 수준으로, 부하 없이 한다.

## §10 코멘트 스냅샷은 왜 "전체 코멘트 수" 인가 (#379 · #384)

closeout-eligible 은 최신 ✅ **이전**의 무마커 코멘트를 "검증자가 이미 확인한 것" 으로
치고 세지 않는다(#379). ④ passed 2번의 사람 코멘트 확인이 그 전제를 참으로 만드는
유일한 자리다.

**전체 수와 사람 수를 헷갈리면 생기는 일**: 사람 코멘트 수를 스냅샷 자리에 적으면, 그게
0 일 때 경계가 0 으로 내려앉아 closeout-eligible 이 PR 의 무마커 코멘트를 **전부** 다시
센다 — #379 가 없앤 바로 그 역방향이다.

**왜 스냅샷 토큰인가**(#384): 그 수는 2번에서 코멘트를 읽은 **시점**을 박아 둔다. 읽기와
✅ 게시 사이(수 초)에 끼어든 사람 코멘트는 ✅ 보다 앞 인덱스에 앉아 "확인된 것" 으로
새는데, closeout-eligible 이 그 수를 경계로 쓰면 그 구간을 다시 집어 경합 창이 닫힌다.

## §11 반쯤 이동한 재디스패치는 왜 이 루프가 안 줍나 (#394)

`verify-redispatch` 가 비0으로 끝난 형상(PR 은 `flow:verify`/`verifying` 상실 · 이슈는
`agent:claimed` 유지)은 세 게이트 전부에서 빠진다 — verify-eligible 도, closeout-eligible
도, eligible-issues 도 안 문다. 그래서 회수 주체를 issue-runner ① Reconcile 로 정했다:
`reconcile.sh` 가 그 형상을 `half_moved_redispatch` 이벤트로 내고 디스패처가 같은 전이를
멱등 재실행한다(`references/state-machine.md` 의 회수 열).

## §12 flake_retry·드레인이 드롭을 만들지 않는 근거

`verify-unpick` 전이가 비0이어도 `verifying` 이 남을 뿐이고 ① 이 고아로 **먼저** 재집으니
드롭은 아니다. 대신 그때 남기는 `BLOCKED: 전이 실패 verify-unpick` 한 줄이, 다음 틱의
`고아 재집` 이 "사망" 이 아니라 "unpick 실패" 였음을 말해 준다.

드레인이 같은 PR 을 두 번 집지 않는 사정: 이번 PR 은 passed→flow:ready 로,
redispatched/held→`verifying` 제거로 이미 큐에서 빠졌다. flake_retry 만 flow:verify 가
남는데(unpick 결과), 그래서 이번 틱에 이미 처리한 PR 번호를 건너뛴다.

드레인이 멈추는 근거: 각 반복은 큐를 최소 1 줄인다(passed→flow:ready 소멸 ·
redispatched/held→`verifying` 소멸 — 출구 전이가 뗀다).

## §13 세 루프의 역할 분담과 컷오버 불변식

- 역할 분담: issue-runner = 생산(구현+결정적CI+PR, `flow:verify` 로 넘김·검증 안 함),
  verify-runner = 검증(E2E+codex 직렬, `머지 판정: ✅` 로 넘김·머지 안 함), closeout =
  마감(머지 독점). 세 루프는 라벨 소유로 충돌을 막는다 — `flow:verify`·`verifying`=
  verify-runner, `harvesting`=closeout(closeout-eligible 은 앞 둘을 제외한다). issue-runner
  는 셋 다 안 건드리고 in-flight 로도 안 센다.
- 컷오버 불변식: verify-runner 가 살아있어야(이 루프가 돌아야) 워커의 `flow:verify`
  PR 이 검증돼 `머지 판정: ✅` 로 흐른다. 이 루프가 죽으면 flow:verify PR 이 검증 없이
  적체하지만(closeout 이 안 집음·issue-runner 도 안 집음) **드롭·오분류는 없다** —
  라벨(`flow:verify` 또는 검증 도중 죽었으면 `verifying`)이 남아 루프 재기동 시 그대로
  재집힌다.
